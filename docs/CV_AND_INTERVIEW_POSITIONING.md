# CV & Interview Positioning — OptiDecarb

## The principle

Do not present OptiDecarb as proof that every line was manually coded without assistance. Present it as an **AI-assisted engineering learning and development project** that you can explain, challenge and validate.

The strongest story is not “I wrote a lot of code”. It is:

> I used AI to help build a serious engineering tool and used the development process to learn modelling, optimization, economics, data validation, professional judgement and technical communication.

## Recommended CV sentence

> **Designed and developed OptiDecarb, an AI-assisted Python learning and screening tool for industrial electrical decarbonization, using the project to develop practical skills in 8,760-hour energy modelling, techno-economic assessment, optimization, data validation and engineering decision-making.**

## More technical CV version

> **Designed and validated OptiDecarb, an AI-assisted Python pre-feasibility tool combining 8,760-hour industrial electricity modelling, linear PV/battery sizing optimization, NPV/payback, CO₂ constraints, sensitivity analysis and a public-data-calibrated Castellón ceramic-industry case.**

## Portfolio / GitHub wording

> OptiDecarb is an AI-assisted engineering project built as both a screening tool and a learning environment. The project emphasizes traceable assumptions, validated model behaviour, transparent limitations and the ability to explain why the model produces a result.

## “Did you code all of this yourself?” — short answer

> I used AI extensively for software development, so I do not claim that I manually wrote every line. I defined the scope, challenged assumptions, validated outputs and used the project to make sure I could explain the model, results and limitations.

## Longer interview answer

> AI was used extensively during the software-development process. I do not present OptiDecarb as a project where I manually wrote every line of code. My focus was to define the engineering problem, decide the scope, challenge assumptions, validate model behaviour, research the public-data case and make sure I could explain the methodology, results and limitations. I used the development process itself as a way to learn engineering and to practise using AI critically rather than accepting generated output blindly.

## If they ask “what was actually your contribution?”

A defensible answer should focus on what you genuinely did and understand. Examples include:

- defining the project objective and scope;
- deciding which technologies and features were deliberately excluded;
- specifying the 8,760-hour modelling workflow;
- requiring transparent economics and carbon accounting;
- requiring regression tests and reproducible reference cases;
- building the public-data Castellón case logic and evidence chain;
- challenging unrealistic or misleading interpretations;
- directing the educational and junior-engineer learning design;
- validating key model outputs and learning how to explain them.

Do not claim a contribution you cannot defend technically.

## What you should understand before listing the project

You should be able to explain, in your own words:

1. MW versus MWh.
2. How PV hourly generation is calculated.
3. Battery power, energy and SOC.
4. Why the model uses 8,760 hours.
5. Baseline and self-sufficiency.
6. CAPEX, OPEX, WACC, CRF, NPV and payback.
7. Why Linear Programming is appropriate for the current formulation.
8. What a binding carbon constraint means.
9. Why battery = 0 is a valid conditional result.
10. Why OMIE is a proxy rather than a full industrial electricity bill.
11. Why ~2.97 MW should often be communicated as “around 3 MWp”.
12. What real data would be needed before an investment decision.
13. What the model does **not** include.
14. How AI was used and how outputs were validated.

## A useful interview mindset

You do not need to pretend that OptiDecarb makes you an experienced energy consultant. A stronger position is:

> The project helped me arrive at a first job less lost. I now recognize the vocabulary, data questions, assumptions, project stages and stakeholder questions that I would expect to meet as a junior engineer.
